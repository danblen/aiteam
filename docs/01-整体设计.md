# 01 — 整体设计

## 分层思路

项目从里到外分了四层，每一层只知道自己下面那一层：

```
┌─────────────────────────────────┐
│  前端 (React)                    │  ← 只管 UI 和 SSE 流消费
│  AppProvider → 组件树            │
└──────────────┬──────────────────┘
               │ HTTP + SSE
┌──────────────┴──────────────────┐
│  后端 (Express)                  │  ← 路由、认证、编排调度
│  routes → runner → CLI adapter  │
└──────────────┬──────────────────┘
               │ spawn / SSH
┌──────────────┴──────────────────┐
│  CLI 适配器 (@danblen/cli)       │  ← 统一三个 CLI 的差异
│  BaseAdapter → claude/opencode/aider │
└──────────────┬──────────────────┘
               │ stdin/stdout
┌──────────────┴──────────────────┐
│  编排引擎 (@danblen/orchestrator) │  ← 纯逻辑，零依赖
│  DAG 编译 → 拓扑执行 → 黑板     │
└─────────────────────────────────┘
```

关键设计决策：**编排引擎和 CLI 适配器是两个独立的 npm 包，都不依赖 HTTP 或 Express**。编排引擎只管"谁先谁后、怎么并行、数据怎么传"，CLI 适配器只管"怎么启动进程、怎么收输出"。后端在中间把它们串起来。

## 为什么拆成两个包

**@danblen/orchestrator** 是一段纯逻辑——输入一个 DAG，输出执行结果。它的 `executeNode` 是一个抽象函数，由调用者注入。这意味着：

- 测试时可以直接 mock `executeNode`，不启动真实 CLI
- 将来换 CLI 实现，编排逻辑不用改
- 编排器可以用在完全不同的场景（不一定是 AI CLI，任何步骤化的任务）

**@danblen/cli** 只关心怎么跟命令行工具打交道。它不知道编排的存在，也不知道 HTTP 的存在。它只知道：给我一个 task、一个工作目录，我 spawn 一个进程，把输出流给你。

## 三种执行模式的设计

项目支持本地、远程、SSH 三种模式。实现上不是三个独立系统，而是通过 **Environment 接口** 统一：

```
interface ExecutionEnvironment {
  mode: 'local' | 'ssh' | 'remote'
  run(task, cliId, signal) → AsyncGenerator<AgentEvent>
  readFiles() → ProjectFile[]
}
```

每种模式实现这个接口。前端的 `send()` 函数只依赖接口，不关心具体模式。切换模式就是换一个 Environment 实例。

### 本地模式

Express 收到请求 → spawn CLI 进程 → stdout 实时回传 → 完成后扫描文件 → 返回。

关键点：CLI 进程直接写磁盘，不需要前端传文件内容。后端只返回文件列表，前端通过 CodeView 按需拉取。

### 远程模式

前端 API 调用通过 `setApiConfig(remoteUrl)` 重定向到远端 Express。实现上是**前端代理**模式——所有 `/api/*` fetch 打到远端，和本地模式走完全一样的后端代码。

但有一个问题：预览 URL。远端构建的预览路径是 `/preview/xxx/`，前端需要拼成远端绝对地址 `https://remote-server/preview/xxx/`。这是通过 SSE done 事件中 `previewUrl` 的前缀替换实现的。

### SSH 模式

通过 `ssh2` 库在远程主机上执行命令。和本地模式的关键区别：

1. CLI 进程在远端运行，但输出通过 SSH 流回传
2. 文件通过 SFTP 同步回来（`syncRemoteFiles` 递归读取远端目录）
3. 命令通过 shell 转义（单引号包裹），防止注入

## 数据流全景

一次完整的"用户输入 → 看到预览"经历了这些步骤：

```
用户输入 "做一个待办清单"
  │
  ├─ 前端: appendMessage('user'), setRun({running: true})
  ├─ 前端: POST /api/conversation/start (扣配额)
  │
  ├─ [多智能体路径]
  │   ├─ POST /api/multi-agent/run  → SSE 连接建立
  │   ├─ buildPlan → compileGraph → validateGraph
  │   ├─ executeGraph 循环:
  │   │   ├─ agent_start 事件 → 前端展示"产品经理开始工作"
  │   │   ├─ delta 事件 × N → 前端流式追加文本
  │   │   ├─ agent_done → 前端记录产物
  │   │   └─ ... 下一个节点
  │   └─ done 事件 → 前端拿到文件列表
  │
  ├─ [单智能体路径]
  │   ├─ createEnvironment(cfg).run()
  │   ├─ 后端 spawn CLI → stdout → SSE delta
  │   └─ done 事件 → 扫描文件 + 启动预览
  │
  └─ 前端: patchCurrent({files, previewUrl}) → setActiveTab('preview')
```

核心设计：**文件始终在后端磁盘上**。前端不传整个文件内容（除了旧版 preview 构建），只传任务描述。这避免了传输大文件的延迟。

## 项目结构怎么映射到职责

```
src/           → 前端 UI + 状态（纯客户端）
server/        → HTTP 路由 + 编排调度（桥接层）
cli/           → CLI 适配器（进程管理）
orchestrator/  → 编排逻辑（纯计算）
shared/        → 跨包共享的常量（仅一个文件）
```

`server/` 是粘合层——它同时 import `cli/` 和 `orchestrator/`，把两者接在一起。`cli/` 和 `orchestrator/` 互不依赖。
