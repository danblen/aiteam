# 04 — 前端状态管理

## 为什么不用 Redux/Zustand

这个项目用纯 React Context 管理全局状态。选择理由：

1. **状态结构是分层的**（sessions > 每个 session 有自己的 runs/queue/files），不适合扁平的 Redux store
2. **高频更新**（SSE 流每秒几十次 delta），需要精确控制重渲染范围，Context + memo 比全局订阅更灵活
3. **没有跨组件通信需求**（不需要 Redux 的 dispatch 模式），状态流是单向的：用户操作 → send() → SSE 事件 → patchCurrent()

代价是 AppProvider 文件很大（~1700 行）。但换来的是状态逻辑高度集中——**所有跟会话/执行/多智能体相关的状态变更都在一个文件里**。

## 核心数据结构设计

```typescript
// 每个会话是一个 Session
sessions: Session[];

// 每个会话的运行状态独立存储（不是全局 run state）
runs: Record<string, RunState>;  // key = session.id

// 消息队列也是按会话隔离
queues: Record<string, QueueItem[]>;

// 当前活跃会话
currentId: string;
current: Session;  // = sessions.find(s => s.id === currentId)
```

关键设计：**多会话可以并发运行**。session A 正在执行 CLI 时，用户切换到 session B 发送新任务，B 也会开始执行。互不阻塞。

实现方式：每个 session 有自己的 `AbortController`（存入 `abortRefs`），自己的 `liveContentRefs`（流式文本缓冲），自己的 `maRunIdRefs`（多智能体 run ID）。切换会话只是换了 `currentId`，后台会话继续运行。

## 流式更新的渲染优化

SSE 流每秒来几十次 delta，如果每次都触发整个组件树重渲染，性能会很差。

解决方案：**mutable ref + 手动 setState**

```javascript
// liveContentRefs: 不触发重渲染的文本缓冲
const liveContentRefs = useRef<Record<string, string>>({});

// delta 事件:
liveContentRefs.current[sid] += event.text;  // 追加到 ref，不触发渲染

// 只在 live 对象引用变化时触发渲染（浅比较）
setRuns(prev => ({
  ...prev,
  [sid]: { ...cur, live: { ...cur.live, content: c, phase: 'writing' } }
}));
```

结合 `memo` 包装组件：

```javascript
// ChatPanel、WorkspacePanel、SessionItem 都是 memo 的
// 它们只在 props 变化时重渲染
// 流式内容通过 live.content 显示，而 live 是 run state 的一部分
```

`SessionItem` 用 `isRunning(id)` 判断是否显示旋转图标——这只在 run state 的 running 布尔值变化时才触发。

## SSE 事件到状态变更的映射

`send()` 函数的本质是一个 SSE 事件处理器。每种事件类型映射到一组状态操作：

```
run_start    → 记录 runId（存入 ref）、日志
plan         → 初始化 maRun.nodeStatus（所有节点状态为 'pending'）
agent_start  → setRun({ live: agent, liveFiles: [] })、更新 maRun.activeNodeId
delta        → liveContentRefs 追加  + setRuns({ live.content })
agent_done   → appendMessage、更新 maRun.nodeStatus[nodeId] = 'done'|'error'
node_skipped → 更新 maRun.nodeStatus[nodeId] = 'skipped'、日志
done         → patchCurrent({ files, framework, previewUrl })、setRun({ running: false })
error        → setRun({ error: msg })
```

每一个事件处理都只修改它需要修改的状态——不会在 delta 事件中触发整个 session 的 patch。

## 工作流 DAG 在 UI 中的体现

`maRun: MaRunState` 是专门为 WorkflowGraph 可视化准备的状态：

```typescript
interface MaRunState {
  workflowId: string | null;
  plan: PlanStep[];                              // 所有步骤
  nodeStatus: Record<string, WorkflowNodeStatus>; // 每个节点的状态
  activeNodeId: string | null;                    // 当前正在执行的节点
}
```

`WorkflowGraph` 组件根据 `nodeStatus` 给节点着色：
- `pending` → 灰色
- `running` → 蓝色 + 脉冲动画
- `done` → 绿色
- `error` → 红色
- `skipped` → 灰色虚线

这不需要轮询，每次 SSE 事件到达时更新 `nodeStatus` 就自动反映到 UI。

## 消息队列的设计

如果当前正在执行一个任务，用户又发了一条消息，怎么办？

```javascript
// 不是简单的"禁止发送"，而是入队:
setQueues(prev => ({
  ...prev,
  [sid]: [...(prev[sid] || []), { id, text, mode }]
}));

// 当 run state 变为 idle 时，自动取下一个:
useEffect(() => {
  const q = queues[sid] || [];
  if (q.length > 0 && !run.running) {
    const [next, ...rest] = q;
    setQueues(prev => ({ ...prev, [sid]: rest }));
    send(next.text, next.mode);
  }
}, [runs, queues, current]);
```

`PromptInput` 组件在 running 状态下显示队列列表而不是发送按钮。用户可以移除队列中的等待项。

## localStorage 持久化的考量

持久化策略很简单：**useEffect 监听状态变化，写 localStorage**。

但有一个陷阱：**iframe 内的 localStorage 污染**。

```
问题: 预览 iframe 加载同源页面 → 另一个 React 实例也写 localStorage 
      → 覆盖主窗口的会话数据

解决: IS_EMBEDDED 检测
  if (window.top !== window.self || location.pathname.includes('/preview/')) {
    // 不写 localStorage
  }
```

所有 `saveSessions`、`saveEnvConfig`、`saveLocalProjects` 都检查 `IS_EMBEDDED`——在预览 iframe 中静默不写。

## 远程模式的 API 重定向

一个巧妙的设计：前端通过 `setApiConfig(prefix, token)` 切换 API 目标：

```javascript
let _apiPrefix = '';   // 默认空 = 本地
let _apiToken = '';

export function apiUrl(path) {
  return _apiPrefix ? `${_apiPrefix}${BASE_PREFIX}${path}` : `${BASE_PREFIX}${path}`;
}
```

远程模式下，`apiUrl('/api/agents')` 变成 `https://remote-server/aiteam/api/agents`。所有 API 函数（listAgents、listWorkflows 等）不需要任何改动——它们都通过 `apiUrl()` 构建 URL。

切换的时机：`useEffect` 监听 `current.envConfig.mode` 变化。

## Environment 工厂模式

```typescript
function createEnvironment(config, sid, projectName, workDir) {
  switch (config.mode) {
    case 'local':  return new LocalEnvironment(config.local, sid, projectName, workDir);
    case 'ssh':    return new SSHEnvironment(config.ssh, sid, projectName);
    case 'remote': return new RemoteEnvironment(config.remote, sid, projectName, workDir);
  }
}
```

每个 Environment 实现相同的接口：`run()` 返回 `AsyncGenerator<AgentEvent>`。前端的 `send()` 只需要 `for await (const event of env.run(...))`，不关心是本地还是远程。

`RemoteEnvironment` 的 `run()` 多做了两件事：
1. **自动项目绑定**：首次发送时，如果没绑定项目，就创建/checkout一个
2. **previewUrl 重写**：把相对路径 `/preview/xxx/` 变成远端绝对地址
