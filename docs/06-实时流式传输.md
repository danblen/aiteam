# 06 — 实时流式传输

## 为什么用 SSE 而不是 WebSocket

这个项目的通信模式是**单向的**：服务器推送数据给浏览器，浏览器只发 HTTP 请求。WebSocket 双向通信的能力用不到。

SSE 的优势：
- 原生 HTTP，不需要升级协议，不需要额外的库
- 浏览器自动重连（EventSource API）
- 可以通过标准 HTTP 中间件（认证、CORS）无需特殊处理
- 断线时 `Last-Event-ID` 头自动发送，服务端可以实现精确续传

实际使用的不是浏览器的 EventSource（因为需要自定义请求头和 POST body），而是手动 fetch + ReadableStream 解析。

## SSE 帧的构建和解析

服务端发送的每一帧格式（手动构造，不用库）：

```
event: agent_start
data: {"index":0,"nodeId":"step-1","agentName":"产品经理"}

```

`\n\n` 是帧分隔符。服务端的 `sendSSE()` 函数很简单：

```javascript
function sendSSE(res, event, data, runId) {
  // 如果有 runId，通过 run-log 系统记录事件（用于断线重连）
  if (runId) {
    const appended = appendRunEvent(runId, event, data);
    if (appended) {
      res.write(appended.frame);  // 已格式化的帧 + id 头
      return;
    }
  }
  // 否则直接写
  res.write(`event: ${event}\n`);
  res.write(`data: ${JSON.stringify(data)}\n\n`);
}
```

前端解析（`consumeSSE()` 和 `runMultiAgent()`）：

```javascript
// 拿到 fetch 的 response.body (ReadableStream)
const reader = response.body.getReader();
let buffer = '';

while (true) {
  const { done, value } = await reader.read();
  buffer += decoder.decode(value, { stream: true });
  
  // 按 \n\n 分割帧
  const frames = buffer.split('\n\n');
  buffer = frames.pop();  // 最后一个可能不完整，留到下次
  
  for (const frame of frames) {
    // 解析 event: 和 data: 行
    const eventMatch = frame.match(/^event: (.+)$/m);
    const dataMatch = frame.match(/^data: (.+)$/m);
    if (eventMatch && dataMatch) {
      yield { type: eventMatch[1], ...JSON.parse(dataMatch[1]) };
    }
  }
}
```

`buffer` 的存在是为了处理 TCP 分片——一个帧可能跨两次 `reader.read()` 到达。

## CLI 输出怎么变成 SSE 事件

从 CLI 进程到浏览器，输出经历了两次转换：

```
CLI stdout (ANSI 文本)
  ↓ stripAnsi() + 逐块回调
BaseAdapter.run() → callbacks.onDelta(text)
  ↓ 
server/multi-agent/runner.js → callbacks.onDelta(text)
  ↓
server/multi-agent/routes.js → sendSSE(res, 'delta', { text })
  ↓ HTTP SSE
前端 lib/multi-agent/run.ts → yield { type: 'delta', text }
  ↓
AppProvider.send() → liveContentRefs 追加 + setRuns
  ↓
ChatPanel → 实时渲染
```

每一步都不要等完整的输出——**流式推送**。CLI 进程写一个 token，前端就显示一个 token。

`stripAnsi()` 剥离 ANSI 转义序列（颜色码、光标控制），因为前端不需要终端控制字符。

## 响应头的重要细节

```
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache, no-transform    ← 禁止代理缓存
Connection: keep-alive                   ← 长连接
X-Accel-Buffering: no                    ← 禁用 Nginx 缓冲
```

`X-Accel-Buffering: no` 特别重要——如果前面有 Nginx 反向代理，默认会缓冲响应。不加这个头，Nginx 会把所有 delta 攒到一起才发给浏览器，流式效果就没了。

`res.flushHeaders()` 确保这些头立即发送，不等 body。

## 断线重连机制

SSE 断线后怎么办？项目实现了基于 run-log 的重连：

### 服务端记录

每次 `sendSSE()` 调用时，如果传了 `runId`，事件会被记录到内存：

```javascript
// run-log.js
const runs = new Map();  // runId → RunRecord

RunRecord = {
  events: [{ id, event, data, ts }],  // 所有发送过的事件
  nextEventId: 1,                      // 递增计数器
  status: 'running',
  abortController: AbortController
}
```

每条事件帧写入时附加 `id` 头：
```
id: 42
event: delta
data: ...
```

限制：最多 64 个 run（LRU）、每个 run 最多 2000 个事件（FIFO）。

### 前端重连

```javascript
// GET /api/multi-agent/run/:runId/events?since=42
// 或通过 Last-Event-ID 头

// 服务端:
const since = req.query.since || req.headers['last-event-id'];
const replay = getEventsSince(runId, since);
// 重放 since 之后的所有事件
for (const ev of replay.events) {
  res.write(`id: ${ev.id}\nevent: ${ev.event}\ndata: ${JSON.stringify(ev.data)}\n\n`);
}
// 如果 run 还在运行中 → 保持连接，继续推送新事件
// 如果 run 已经结束 → 关闭连接
```

## 客户端断开检测

服务端怎么知道客户端断开了？监听 `res` 的 `close` 事件：

```javascript
res.on('close', () => {
  if (!res.writableEnded) {
    controller.abort();  // 中止上游请求或 CLI 进程
  }
});
```

监听的是 `res` 而不是 `req`——`req` 的 `close` 可能在 body 读完时就触发，不代表客户端断开。

**重要设计决定：断线不中止 run**。只有显式 POST `/api/multi-agent/abort` 才会中止。断线只是停止推送事件，run 在后台继续执行。用户可以重连回来。

## AbortController 的传播链

中止信号需要穿透三层：

```
用户点击"停止"
  ↓
前端 abortController.abort()
  ↓
前端 fetch 被 abort → HTTP 连接断开
  ↓ (并行)
前端 POST /api/multi-agent/abort → 后端 abortRun(runId)
  ↓
后端 runRecord.abortController.abort()
  ↓
编排器的 ctx.signal 触发 → executeGraph 停止调度
  ↓
BaseAdapter.run() 的 signal 触发 → 子进程被 kill('SIGTERM')
```

两条路径**同时触发**：前端 fetch abort 断开 SSE 连接，后端 abort 确保 run 真正停止。只断开 SSE 不够（run 还在后台跑），只 abort run 也不够（SSE 连接还开着）。

## 流式输出的 LiveTurn 管理

前端的 `LiveTurn` 对象代表"正在流式输出的智能体"：

```typescript
interface LiveTurn {
  agent: AgentRole;
  content: string;               // 累积的流式文本
  phase: 'thinking' | 'writing';  // thinking = 还没收到第一个 token
}
```

`phase` 的实现：
- 智能体开始时 → `{ phase: 'thinking' }`（ChatPanel 显示转动动画）
- 第一个 delta 到达 → `{ phase: 'writing' }`（切换为流式文本渲染）

这是一个小细节：用户看到"思考中…"的动画比看到空白要好，即使实际等待时间不到一秒。
