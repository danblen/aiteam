# 02 — 多智能体编排

## 要解决什么问题

多个 AI 角色协作时，面临三个问题：

1. **顺序**：谁先谁后？哪些可以并行？
2. **上下文传递**：上一步的产出怎么传给下一步？
3. **冲突处理**：并行执行时，两个智能体写了同一个文件怎么办？

编排引擎就是解决这三个问题的一段纯逻辑。

## 从 Plan 到 DAG

用户选定智能体序列后，后端调用 `buildPlan()` 把它变成 Plan：

```
用户选择: [产品经理, 设计师, 工程师]
     ↓
Plan: [
  { agent: 产品经理, step: { dependsOn: [] } },
  { agent: 设计师,   step: { dependsOn: [] } },
  { agent: 工程师,   step: { dependsOn: [] } }
]
```

如果选了工作流，则从预定义的步骤展开。WorkflowStep 可以显式声明 `dependsOn`、`fileScope`、`condition` 等。

然后 `compileGraph()` 把 Plan 编译成 DAG：

```
dependsOn 为空 → 默认依赖前一个节点（顺序链）
dependsOn 非空 → 只依赖指定的节点（显式边）

示例：设计师 + 评审都依赖产品经理，但互不依赖 → 可以并行
产品经理 ──┬── 设计师 ──┬── 工程师
           └── 评审 ────┘
```

`topologicalLevels()` 把节点按拓扑层级分组，同一层级的节点**没有相互依赖**，理论上可以并行。

## 并行调度怎么决定谁可以同时跑

光有 DAG 还不够。两个节点可能拓扑层级相同，但如果它们都可能写 `src/App.tsx`，就不能同时跑。

**文件域（fileScope）** 机制解决这个：

```javascript
// scope.js 的核心逻辑
function scopesOverlap(scopeA, scopeB) {
  if (scopeA.length === 0 || scopeB.length === 0) return true; // 空 = 全局锁
  // 检查 glob 前缀是否可能指向相同文件
  for (const a of scopeA)
    for (const b of scopeB)
      if (a.startsWith(b) || b.startsWith(a)) return true;
  return false;
}
```

`pickParallelBatch()` 在每轮调度时，从就绪节点中贪婪选择：只读节点总能并行，写节点需要 fileScope 互不冲突。

```
示例：设计师(fileScope: ['src/assets/']) 和 工程师(fileScope: ['src/components/'])
→ 不重叠 → 可以并行

设计师(fileScope: []) 和 工程师(fileScope: ['src/'])
→ 设计师是全局锁(空=全局) → 不能并行
```

## 黑板模式怎么传递上下文

编排器里有一个 `Blackboard` 类。每个节点执行完，结果写入黑板。后续节点的任务模板可以从黑板取值：

```
产品经理执行完 →
  blackboard.setNode('pm', { contract: { summary: "需要一个支持增删改的待办清单" } })

工程师的 taskTemplate 引用:
  "产品经理说：{{nodes.pm.contract.summary}}。请用 React 实现。"
  ↓ renderTask() 插值后:
  "产品经理说：需要一个支持增删改的待办清单。请用 React 实现。"
```

这比把上一步整个输出文本拼进去要好——结构化数据让每个智能体只看到它需要的部分。

**prevContract 的智能合并**：当一个节点依赖多个前驱节点时，`prevContractOf()` 会自动合并所有依赖方的 contract：

```javascript
function prevContractOf(node, blackboard) {
  // 对 node.dependsOn 中的每个前驱:
  //   summary → 拼成 "[id1] xxx\n\n[id2] yyy"
  //   files → 去重合并
  //   notes → 拼接
}
```

## 条件执行怎么实现

`conditions.js` 实现了一个受限的表达式语言，**不用 eval**：

```
// 语法（手写解析器，不是 eval）
nodes.pm.contract.summary contains "增删改"  → true/false
nodes.designer.exitCode == 0                  → true/false
input contains "React"                         → true/false
(空字符串)                                      → true (默认执行)
```

实现原理：正则匹配 `contains` / `==` / `!=` / `exists`，从 `blackboard.view()` 取值，比较后返回布尔值。无法识别的语法返回 `true`（保守策略：宁可多执行，也不错杀）。

## 重试与超时

这两个机制实现在 `runNodeWithRetry()` 里，不依赖外部重试库：

```
maxAttempts=3, backoffMs=2000 的节点:
  第1次执行 → 失败 (exitCode != 0)
  等待2秒
  第2次执行 → 失败
  等待2秒
  第3次执行 → 成功/失败 → 返回结果
```

超时实现：`setTimeout` + `child.kill('SIGTERM')` + 3 秒后 `SIGKILL`。和 AbortSignal 共用同一套 kill 逻辑。

## Supervisor 模式的设计

前面说的 DAG 适用于"步骤已知"的场景。但如果不知道需要多少步呢？

Supervisor 模式的设计思路：**让 AI 自己做调度决策**。

```
每一轮:
  1. 把当前状态（用户任务 + 已完成步骤 + 工作区文件 + 历史决策）发给监督者 agent
  2. 监督者输出 JSON 决策: { action: "run"/"parallel"/"done", agents: [...] }
  3. 解析决策，执行选定的智能体
  4. 结果写入黑板
  5. 重复，直到决策 action="done" 或达到 maxIterations(12)
```

监督者本身也是一个 agent（默认用智能体池中的第一个）。它的 system prompt 被替换为 `SUPERVISOR_SYSTEM`，强制它输出 `supervisor-decision` 格式的 JSON。

为什么不用 LangChain 或类似的 agent 框架？因为这个项目要自己控制调度逻辑——每个节点的超时、重试、fileScope、onFailure 策略都不同，现成框架做不到这样的细粒度控制。

## onFailure 策略

```
continue          → 节点失败不影响后续（默认）
skip-dependents   → 失败后，所有依赖此节点的后续节点都被跳过
abort             → 失败后整个 DAG 中止
```

`skip-dependents` 的传播是递归的——如果 A 失败且 onFailure=skip-dependents，B 依赖 A，则 B 被跳过；C 依赖 B，则 C 也被跳过（即使 C 不直接依赖 A）。

## 图校验

编译后的 DAG 会经过 `validateGraph()` 校验：

1. **循环检测**：DFS 遍历，发现环就报错
2. **依赖完整性**：检查 `dependsOn` 引用的节点是否存在
3. **自引用**：节点不能依赖自己
4. **并行写冲突预警**：同一拓扑层级、重叠 fileScope 的两个写入节点 → warning（不是 error，因为 fileScope 是用户手动配置的，可能是有意为之）
