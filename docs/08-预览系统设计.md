# 08 — 预览系统设计

## 要解决的问题

AI 生成代码之后，用户需要"立即看到效果"。预览系统的核心问题是：**如何把磁盘上的一组源文件变成一个浏览器可以访问的页面**。

React 项目不能像 HTML 一样直接用浏览器打开——需要构建工具解析 JSX、打包模块、处理导入。

## 两条预览路径

项目提供了两种预览方式，各有不同的适用场景：

| | 静态构建 (preview.js) | Dev Server (preview-dev.js) |
|---|---|---|
| 原理 | Vite build → 输出 dist/ → express.static 服务 | Vite 中间件模式，即时编译 |
| 速度 | 慢（需要完整构建） | 快（按需编译，无构建步骤） |
| 适用 | 旧版"前端传文件"模式 | CLI 直接写磁盘的模式 |
| 入口 | `POST /api/preview/:sid` | `POST /api/preview/:sid/dev` |
| 文件来源 | 前端传 `{ files: [...] }` | 从 `workDir` 磁盘读取 |
| 缓存 | 有（构建产物持久化） | 无（内存编译，重启丢失） |

静态构建路径是历史遗留的——早期项目是"单文件 HTML"模式，前端把 AI 生成的代码传上来构建。现在主要使用的是 Dev Server 路径：**CLI 已经把代码写到了磁盘上，直接用 Vite 中间件服务源文件**。

## React 项目怎么构建：入口注入问题

CLI 生成的 React 项目不一定会带有正确的 `index.html`。Vite 需要一个入口 HTML 文件来知道从哪里开始打包。

`patchEntry()` 解决了这个问题：

```javascript
// 问题: CLI 可能只生成了 src/App.tsx 和 src/main.tsx，
//       但没有 index.html，或者 index.html 里的 <script src> 不对
//
// 解决:
function patchEntry(dir) {
  // 1. 确保有 index.html (没有就生成一个最小骨架)
  // 2. 按优先级找入口文件:
  //    src/main.jsx → main.tsx → index.jsx → index.tsx → app.jsx → ...
  // 3. 替换 <script type="module" src="..."> 或注入新标签
}
```

注入位置的选择：如果 `index.html` 里有 `<div id="root">`，就把 `<script>` 标签插在 `</body>` 之前。这是标准的 Vite 入口位置。

## Dev Server 的模块解析问题

CLI 生成的项目目录里**没有 `node_modules/`**，但代码里有 `import React from 'react'`。Vite 怎么找到这些包？

答案是 `resolveFromAppModules()` 这个自定义 Vite 插件：

```javascript
// Vite 中间件模式下，预览项目的 node_modules 解析会失败
// 因为这个项目目录没有 npm install
//
// 插件的思路: Vite 自己的解析器失败了 → 从主应用的 node_modules 里找
function resolveFromAppModules() {
  return {
    name: 'vite:resolve-app-modules',
    enforce: 'post',           // 在 Vite 默认解析失败之后再执行
    resolveId(id, importer) {
      // 只处理裸导入 (bare import)，比如 'react'、'react-dom/client'
      if (id.startsWith('.') || id.startsWith('/')) return null;  // 相对路径不处理
      
      // 从主应用的 node_modules 里找
      try {
        const resolved = appRequire.resolve(id, { paths: [APP_ROOT] });
        if (resolved.startsWith(APP_NODE_MODULES)) {
          return { id: resolved, external: false };
        }
      } catch { /* 找不到就交给 Vite 报错 */ }
    }
  };
}
```

`appRequire` 是用 `createRequire(path.join(APP_ROOT, 'package.json'))` 创建的——它强制从主应用的角度解析模块路径，不是从预览项目目录。这样 `import React from 'react'` 就指向了主应用安装的 React。

同时 Vite 配置里设置了 `fs.allow: [workDir, APP_NODE_MODULES]`——允许 Vite 访问工作目录**和**主应用的 node_modules（默认为安全会阻止工作目录外的文件访问）。

## Vite 中间件模式的设计

```javascript
const vite = await createServer({
  root: workDir,              // 以工作目录为根
  base: '/aiteam/preview/sid/', // 所有资源 URL 加此前缀
  server: {
    middlewareMode: true,     // 不启动 HTTP 服务器，只作为中间件
    hmr: false,               // 关闭热更新（预览不需要）
  },
  appType: 'spa',             // SPA 模式（路由 fallback 到 index.html）
  plugins: [
    react({ fastRefresh: false }),  // 关闭 Fast Refresh（预览不需要）
    resolveFromAppModules(),
  ],
});
```

为什么关闭 HMR 和 Fast Refresh？因为预览文件是 AI **一次性生成**的，没有编辑-保存-刷新的工作流。开启 HMR 反而消耗资源。

`middlewareMode: true` 意味着 Vite 不监听端口，而是作为一个 Express 中间件接入现有服务器：

```javascript
// mountDevPreview 中注册的中间件:
app.use('/preview/:sid', (req, res, next) => {
  const entry = servers.get(sid);
  if (!entry) return next();  // 没有 Dev Server → 交给静态文件服务
  
  entry.vite.middlewares(req, res, next);  // 代理到 Vite
});
```

**中间件注册顺序很关键**：`mountDevPreview` 必须在 `mountPreview` **之前**注册。当有 Dev Server 时，请求被 Dev Preview 中间件拦截；没有时，`next()` 落到后面的静态文件服务。

## base 路径的计算

```
APP_BASE_PATH = '/aiteam'  (或从环境变量)
Dev Server base = '/aiteam/preview/<sid>/'
```

为什么需要这个 base？因为 `vite.config.ts` 里配置了 `base: '/aiteam/'`，所有应用资源都在 `/aiteam/` 下。如果预览也走同样的 NGINX 反向代理，它的资源路径必须是 `/aiteam/preview/<sid>/`。

但实际上，**在代码编辑器的 iframe 中，预览页面是独立加载的**——它不是主应用的子路由。iframe 的 `src` 直接指向后端端口，跨过了 Vite 代理。所以 `resolvePreviewUrl()` 要分情况处理：

```javascript
function resolvePreviewUrl(previewUrl, remoteBase) {
  if (previewUrl.startsWith('http')) return previewUrl;  // 已经是绝对 URL
  
  // 远程模式: 拼上远端地址
  if (remoteBase) return `${remoteBase}/aiteam${previewUrl}`;
  
  // 本地模式: 只拼 BASE_PREFIX
  return `/aiteam${previewUrl}`;
}
```

## 空闲清理策略

Dev Server 是内存常驻的，不能一直开着。设计了一个基于最后访问时间的自动清理：

```
每个 Dev Server 记录 lastAccess
每 5 分钟扫描一次
lastAccess 超过 30 分钟 → 关闭 Vite 实例，删除条目
```

访问刷新：每次 `startDevServer()`（返回缓存的 URL）和每次中间件处理请求时，都更新 `lastAccess`。所以只要用户在看预览，就不会被清理。

进程退出时（SIGTERM/SIGINT）调用 `stopAll()`，优雅关闭所有 Vite 实例。

## 旧版"前端传文件"构建路径

虽然现在主要用 Dev Server，但旧版路径仍然有一些值得讲的设计：

```
POST /api/preview/:sid   { files: [...], framework: 'react' }
  ↓
withLock(sid, fn)  ← 同一个 sid 的并发请求排队
  ↓
resetDir(dir)  ← 清空旧构建，防止残留文件污染
  ↓
writeFiles(dir, files)  ← 把前端传来的文件写到磁盘
  ↓
framework === 'react' ?
  buildReact():  ← 懒加载 vite + @vitejs/plugin-react（启动时不加载）
    patchEntry() → vite.build({ root: dir, ... })
  或
  buildHtml():   ← 直接复制 index.html 到 dist/
  ↓
express.static(distDir)  ← 静态服务构建产物，缓存 handler 避免重复创建
  ↓
返回 URL: /preview/<sid>/
```

### 为什么懒加载 vite

```javascript
const { build } = await import('vite');
const react = (await import('@vitejs/plugin-react')).default;
```

`import()` 只在第一次构建时执行。如果服务启动后从未触发过预览构建，vite 就不会加载到内存。这对启动速度和内存占用有帮助——因为可能很多请求根本不用预览。

### 序列化锁

```javascript
function withLock(sid, fn) {
  const prev = locks.get(sid) || Promise.resolve();
  const next = prev.then(fn, fn);
  locks.set(sid, next.catch(() => {}));
  return next;
}
```

同一个 sid 的并发构建请求（比如用户点了多次"刷新"）会被串行化——第二个请求等第一个完成后再执行，而不是两个构建同时跑互相踩文件。

### 静态文件服务的 fallthrough:false

```javascript
handler = express.static(dir, { index: 'index.html', fallthrough: false });
```

这个 `fallthrough: false` 很关键。如果没有它，预览资源缺失时（比如请求一个不存在的 chunk），Express 不会返回 404，而是 `next()` 到后面的路由。问题是后面有 SPA 的 `app.get('*')` 通配路由——**它会返回主应用的 index.html**。

那会在预览 iframe 里加载一份完整的主应用。同源下，如果主应用写 localStorage，它会覆盖父窗口的会话数据。`fallthrough: false` 确保缺失资源直接返回 404，不触发 SPA fallback。

## 预览 URL 的完整链路

以多智能体模式为例：

```
1. executeGraph 完成 → scanWorkspace() → files[]
2. finishWithPreview() 调用 startDevServer(sid, workDir)
3. 返回 previewUrl = '/preview/<sid>/'
4. SSE done 事件: { files, previewUrl, workDir }
   ↓
5. 前端收到 done 事件:
   resolvePreviewUrl(previewUrl, remoteBase)
     → 本地: '/aiteam/preview/<sid>/'
     → 远程: 'https://remote-server/aiteam/preview/<sid>/'
6. patchCurrent(sid, { previewUrl: fullUrl })
7. setActiveTab('preview')
   ↓
8. PreviewTab 渲染:
   <iframe src={previewUrl} key={reloadKey} />
   reloadKey 变化 → iframe 重新加载
```

`reloadKey` 的作用：如果两次 done 返回了相同的 URL（比如 rebuild），`useEffect` 里 `setReloadKey(k => k + 1)` 导致的 key 变化会让 React **卸载旧 iframe 并创建新的**，强制浏览器重新请求。直接改 `src` 在某些情况下不会触发重载。

## iframe 的 sandbox 策略

```html
<iframe sandbox="allow-scripts allow-forms allow-modals allow-popups allow-same-origin" />
```

- `allow-scripts` — 允许执行 JavaScript（预览的 React 应用需要）
- `allow-forms` — 允许表单（应用的交互功能）
- `allow-same-origin` — 允许同源访问（预览页面和主应用在同一域下，localStorage 可访问）
- **不开启** `allow-top-navigation` — 防止预览页面跳转父窗口
- **不开启** `allow-popups-to-escape-sandbox` — 防止弹窗跳出沙箱

`allow-same-origin` 是双刃剑——预览页面能访问主应用的 localStorage（所以主应用有 `IS_EMBEDDED` 检测）。但不开它的话，很多需要 cookie/localStorage 的 React 应用会不正常。
