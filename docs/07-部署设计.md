# 07 — 部署设计

## Docker 镜像分层策略

Dockerfile 的设计思路：**运行时依赖在镜像里，应用代码挂载进来**。

```dockerfile
FROM node:22-bookworm-slim
RUN apt-get install -y git sudo
RUN npm install -g @anthropic-ai/claude-code opencode-ai
RUN useradd sandbox-10000 ... sandbox-10199  # 预创建 200 个用户
WORKDIR /app
CMD ["node", "server/index.js"]
```

为什么代码不在镜像里？

```
传统方式:  代码变更 → docker build → docker push → docker pull → restart
               ↑ 每次改代码都要重新构建镜像（慢）

本项目:    代码变更 → npm run build → docker restart
               ↑ 代码通过 volume 挂载，只需重启容器（快）
```

这种设计适合**单机部署**——应用代码在宿主机上，通过 `-v /host/app:/app` 挂载进容器。CI/CD 只做 `git pull + npm install + npm run build + docker restart`。

代价是镜像不能独立运行（需要挂载代码），不适合 Kubernetes 的 Pod 调度。但这是一个单机项目，不需要多副本。

## 开发服务器的端口发现

`dev.js` 的端口分配逻辑：

```javascript
async function findPortPair(baseFe) {
  let fe = baseFe;
  while (!(await portAvailable(fe) && await portAvailable(fe + 10))) {
    fe++;  // 有一个被占用，整体偏移
  }
  return { fe, be: fe + 10 };
}
```

为什么 FE 和 BE 间隔 10 个端口？因为预览 Dev Server 还要用额外的端口。预留间隙防止冲突。

环境变量 `FE_PORT` 和 `SERVER_PORT` 可以跳过自动发现，直接用指定端口——这在预览代理场景中很重要（预览代理需要知道 Vite 的确切端口）。

## Vite 配置中的关键决策

```typescript
// vite.config.ts
export default defineConfig({
  base: '/aiteam/',          // 所有资源路径加 /aiteam/ 前缀
  server: {
    host: true,              // 监听所有网卡，包括 IPv4 127.0.0.1
    watch: {
      ignored: [
        '**/server/.previews/**',    // 预览构建输出
        '**/server/.published/**',   // 发布构建输出
        '**/server/.data/**',        // 后端数据
      ]
    },
    proxy: {
      '/aiteam/api': {              // 开发时代理 /api 到后端
        target: `http://localhost:${SERVER_PORT}`,
        rewrite: (p) => p.replace(/^\/aiteam/, ''),
      },
      '/aiteam/preview': { ... },   // 预览路由也代理
      '/aiteam/p': { ... },         // 发布路由也代理
    }
  }
});
```

`host: true` 解决了一个 macOS 上的具体问题：默认只监听 IPv6 `[::1]`，浏览器用 `127.0.0.1` 解析 `localhost` 时连不上。

`watch.ignored` 很重要——后端在运行时会在 `server/` 目录下写入大量文件（预览构建、发布输出、数据文件）。如果不忽略，Vite 的 HMR 会触发整页刷新。

## Monorepo 设计

项目用 npm workspaces 管理两个独立包：

```json
{
  "workspaces": ["cli", "orchestrator"]
}
```

两个包都是 `type: module`（ESM），各自有独立的 `package.json`：

```
@danblen/cli           - CLI 适配器
@danblen/orchestrator  - 编排引擎
```

发布时分别 publish：
```bash
npm publish -w @danblen/cli --access public
npm publish -w @danblen/orchestrator --access public
```

这样设计的好处：如果其他项目只需要 CLI 适配器（不需要编排），可以单独安装 `@danblen/cli`。如果只需要编排引擎（用自己的 CLI 实现），可以单独安装 `@danblen/orchestrator`。

## CI/CD 流程

```
push main/team → GitHub Actions
  ├── job: build
  │     npm ci → npm run build → upload dist/ artifact
  ├── job: deploy-pages
  │     下载 artifact → deploy to GitHub Pages (静态前端)
  ├── job: deploy-aliyun
  │     SSH → git pull → npm install → npm run build → docker restart aiteam
  └── job: deploy-aws
        SSH → 同上
```

阿里云和 AWS 的部署是完全独立的——代码推一次，两个云都更新。用 `workflow_dispatch` 也可以手动选择只部署一个目标。

## 资源限制策略

容器级别的限制（`docker run` 参数）：
```
--memory 1.4g --memory-swap 1.7g --cpus 1.5
```

容器内还有 cgroup v2 的**每会话限制**（`setCgroupLimits`）：
```
memory.max = 512m per session
cpu.max = 50000 100000 (50% of one CPU)
```

两层限制的目的不同：容器限制防止影响宿主机，会话限制防止一个用户占满容器。

## 数据持久化

所有持久化数据都在 `server/` 目录下：

```
server/.data/users.json              # 用户注册信息
server/.data/secret                  # HMAC 签名密钥
server/.data/agents.json             # 自定义智能体
server/.data/workflows.json          # 自定义工作流
server/.data/projects.json           # 项目注册表
server/.published/registry.json      # 发布注册表
```

没有用数据库。选择 JSON 文件的原因：
- 数据量小（用户数、项目数在可控范围）
- 不需要并发写入（每个用户的数据通过 `withLock` 串行化）
- 部署简单，不需要额外的数据库容器
- 备份简单（直接复制目录）

`withLock` 的实现：每个文件一个 Promise 链，保证同一个文件的读写不会交错：

```javascript
const locks = new Map();

function withLock(file, fn) {
  const prev = locks.get(file) || Promise.resolve();
  const next = prev.then(fn).finally(() => {
    if (locks.get(file) === next) locks.delete(file);
  });
  locks.set(file, next);
  return next;
}
```

这就是一个简单的"文件级互斥锁"，不需要外部锁服务。

## 环境变量设计

认证和密钥通过环境变量注入，不写死在代码里：

```
API_TOKEN         → 远程访问的 Bearer token（用于跨服务调用）
ADMIN_EMAIL       → 管理员的邮箱（默认 q@q.qq）
AUTH_SECRET       → HMAC 签名密钥（不设置则自动生成）
AUTH_REQUIRED     → 强制登录模式
ANTHROPIC_API_KEY → 透传给沙箱中的 claude 进程
OPENAI_API_KEY    → 透传给沙箱中的 opencode/aider 进程
```

密钥的传递链路：`process.env` → `spawnAsUser` 的 `env` → 子进程的环境变量。密钥不在 Express 代码中使用，只做透传。
