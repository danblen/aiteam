## 总体架构概览

Cloud AI Team 的安全可信与全程可观测，可以理解为以下几层共同作用：

```text
用户发起任务
   ↓
控制平面：身份认证、租户校验、任务创建
   ↓
执行平面：为任务创建独立 Sandbox
   ↓
Agent Runtime：规划、推理、调用工具、修改文件、执行命令
   ↓
策略引擎：权限检查、高危命令拦截、审批控制
   ↓
事件总线：记录每一步行为
   ↓
SSE Gateway：向前端实时推送事件
   ↓
审计存储：持久化日志，支持回放、审计、追踪
```

关键能力可以拆成四句话：

1. **Agent 不在共享环境里乱跑，而是在独立 Sandbox 中执行。**
2. **租户之间的代码、上下文、凭据、日志、缓存都严格隔离。**
3. **Agent 的每一步行为都被转成标准事件，通过 SSE 实时推送。**
4. **所有事件都会留下 trace 和审计记录，可追踪、可回放、可审计。**

## 独立 Sandbox：每个 Agent 都运行在隔离环境中

Cloud Agent 接收到任务后，不会直接在宿主机或共享环境中执行代码，而是为当前任务创建一个独立运行环境。

### 典型流程

```text
用户提交任务
   ↓
平台创建任务会话
   ↓
启动独立 Sandbox
   ↓
加载当前任务所需的代码上下文
   ↓
Agent 在 Sandbox 内读文件、改代码、跑命令、调用工具
   ↓
执行结果通过事件流返回
   ↓
任务结束后 Sandbox 销毁或回收
```

### Sandbox 通常会提供哪些隔离？

| 隔离维度 | 说明 |
|---|---|
| 文件系统隔离 | Agent 只能访问当前任务授权的工作区，不能读取其他租户文件 |
| 进程隔离 | 不同任务的进程彼此不可见 |
| 网络隔离 | 默认限制出站访问，只允许访问授权服务或域名 |
| 资源隔离 | CPU、内存、磁盘、执行时长受限，防止任务失控 |
| 环境变量隔离 | 不同任务不会共享敏感环境变量 |
| 凭据隔离 | 临时凭据只注入当前 Sandbox，不长期暴露 |
| 生命周期隔离 | 任务结束后环境销毁，减少残留数据 |

### 为什么 Sandbox 很关键？

Agent 会执行很多实际操作，例如：

- 读取代码文件；
- 修改源码；
- 运行测试；
- 安装依赖；
- 执行 shell 命令；
- 调用外部工具；
- 创建 commit 或 PR。

如果这些行为直接发生在共享环境中，风险很高。

Sandbox 的作用是把 Agent 的行为限制在一个可控、可销毁、可审计的边界内。

## 租户间零数据渗透：靠系统边界，而不是模型自律

“零数据渗透”不能靠提示词约束模型，而要靠平台底层的强制隔离。

### 1. 租户身份贯穿全链路

每个任务都会带有租户、项目、会话等标识：

```json
{
  "tenant_id": "tenant_abc",
  "workspace_id": "ws_123",
  "project_id": "project_456",
  "session_id": "agent_session_789",
  "task_id": "task_001"
}
```

后端所有资源访问都必须通过这些身份进行鉴权：

- 代码仓库；
- 项目上下文；
- 文件内容；
- 检索索引；
- 向量库；
- 缓存；
- 日志；
- 工具调用；
- SSE 事件订阅；
- 最终产物。

也就是说，租户 A 的 Agent 无法访问租户 B 的资源，因为底层权限体系根本不允许。

---

### 2. 代码上下文隔离

Cloud Agent 通常会使用项目上下文来理解代码，例如：

- 文件结构；
- 代码搜索结果；
- 符号定义；
- 函数调用关系；
- embedding 检索结果；
- 历史修改记录；
- 测试输出。

为了避免跨租户泄露，平台需要做到：

```text
租户 A 的代码上下文只能进入租户 A 的 Agent 会话。
租户 B 的任务不能命中租户 A 的索引、缓存或检索结果。
```

常见实现方式包括：

- 索引按租户或项目分区；
- embedding 检索结果按租户隔离；
- 上下文缓存不跨租户复用；
- 临时文件按任务隔离；
- 任务结束后清理中间产物。

---

### 3. 凭据和密钥隔离

Agent 在执行任务时可能需要访问：

- Git 仓库；
- 包管理器；
- 私有 npm / pip registry；
- CI 服务；
- API 服务；
- 数据库；
- 部署平台。

安全平台通常不会把长期密钥直接交给模型，而是采用最小权限机制：

```text
Agent 请求访问某个服务
   ↓
平台检查当前任务是否有权限
   ↓
平台生成短期 token 或由平台代理执行
   ↓
Sandbox 内完成任务
   ↓
凭据不进入模型上下文，不写入日志，不跨任务复用
```

例如：

```text
Agent：需要 clone 仓库
平台：校验任务权限
平台：使用临时 token clone
Sandbox：拿到代码文件
Agent：不直接持有长期 GitHub token
```

这能降低 prompt injection、恶意命令、数据外泄等风险。

---

### 4. 网络隔离与出口控制

Cloud Agent 的 Sandbox 通常不会允许任意访问互联网。

常见策略：

```text
默认禁止出站访问
   ↓
仅允许白名单域名或服务
   ↓
记录所有外部请求
   ↓
拦截异常上传或敏感数据外发
```

例如允许：

- 当前仓库地址；
- 官方包管理器；
- 企业授权的私有 registry；
- 测试服务；
- 日志服务。

限制：

- 任意 HTTP POST；
- 未知外部域名；
- 内部元数据服务；
- 其他租户服务；
- 非授权生产系统。

## SSE 实时可观测：把 Agent 行为事件化

所谓“全程可观测”，本质上是把 Agent 的执行过程拆成一系列事件。

传统 LLM 调用可能是：

```text
用户输入 → 模型返回最终结果
```

但 Cloud Agent 的执行过程是：

```text
用户输入
   ↓
Agent 理解任务
   ↓
生成计划
   ↓
搜索代码
   ↓
读取文件
   ↓
修改文件
   ↓
运行命令
   ↓
查看测试结果
   ↓
继续修复
   ↓
生成总结
任务结束
```

这些行为都会被转成事件。

---

## SSE 是什么？

SSE，Server-Sent Events，是一种基于 HTTP 的服务端单向实时推送机制。

它非常适合 Agent 场景，因为 Agent 的行为天然是流式的：

- 模型输出是流式的；
- 工具调用是逐步发生的；
- 命令执行有实时输出；
- 文件修改会产生 diff；
- 测试结果会陆续返回；
- 错误可能随时出现。

### SSE 简化流程

```text
前端发起 Agent 任务
   ↓
前端订阅事件流，例如 /agent/events?session_id=xxx
   ↓
服务端建立 SSE 长连接
   ↓
Agent Runtime 持续产生事件
   ↓
服务端通过 SSE 推送给前端
   ↓
前端实时渲染思考过程、工具调用、文件变更、命令输出
```

---

## 事件流示例

### Agent 消息事件

```json
{
  "session_id": "agent_session_789",
  "step_id": "step_001",
  "type": "agent_message",
  "content": "我先定位登录失败的相关代码。"
}
```

### 工具调用事件

```json
{
  "session_id": "agent_session_789",
  "step_id": "step_002",
  "type": "tool_call",
  "tool": "search_code",
  "input": {
    "query": "login authentication middleware"
  }
}
```

### 工具结果事件

```json
{
  "session_id": "agent_session_789",
  "step_id": "step_003",
  "type": "tool_result",
  "tool": "search_code",
  "result_summary": "找到 8 个相关文件",
  "duration_ms": 320
}
```

### 文件修改事件

```json
{
  "session_id": "agent_session_789",
  "step_id": "step_004",
  "type": "file_edit",
  "path": "src/auth/middleware.ts",
  "action": "modify",
  "diff_summary": "修复 token 校验逻辑"
}
```

### 终端命令事件

```json
{
  "session_id": "agent_session_789",
  "step_id": "step_005",
  "type": "terminal_command",
  "command": "npm test",
  "exit_code": 0,
  "duration_ms": 18342
}
```

前端拿到这些事件后，就可以实时展示：

- Agent 当前在想什么；
- Agent 调用了什么工具；
- Agent 读了哪些文件；
- Agent 改了哪些代码；
- Agent 运行了什么命令；
- 测试是否通过；
- 哪一步失败；
- 为什么失败。

## 每一步思考如何被观测？

这里需要区分一个概念：

> “每一步思考”通常指平台能够捕获到的模型输出、推理事件、计划步骤和决策记录，而不是模型内部所有黑箱状态。

如果模型本身提供 reasoning / thinking tokens，平台可以记录：

```json
{
  "type": "reasoning",
  "content": "用户要求修复测试失败，我应该先查看 CI 日志，再定位失败用例。"
}
```

如果模型不提供内部推理过程，平台可以记录：

- 用户输入；
- Agent 生成的计划；
- 模型输出内容；
- 工具选择理由；
- 工具调用输入；
- 工具调用结果；
- Agent 根据结果做出的下一步决策；
- 最终总结。

也就是说，Cloud Agent 的可观测性并不是“读心术”，而是：

> 把 Agent 与外部世界交互的每一个关键动作都事件化、日志化、可追踪化。

## 每一次工具调用如何被记录与控制？

Cloud Agent 通常不会让模型直接执行命令或访问系统，而是经过一个工具代理层。

### 工具调用流程

```text
模型提出工具调用请求
   ↓
Agent Runtime 接收请求
   ↓
策略引擎检查权限
   ↓
Sandbox 执行工具
   ↓
记录输入、输出、耗时、退出码
   ↓
推送 SSE 事件
   ↓
写入审计日志
   ↓
结果返回给模型继续推理
```

### 示例：模型请求运行命令

模型可能希望执行：

```bash
npm test
```

平台不会直接让模型碰到 shell，而是这样处理：

```text
模型请求：run_command("npm test")
   ↓
平台检查：该任务是否允许执行测试命令
   ↓
平台检查：路径是否越权
   ↓
Sandbox 执行命令
   ↓
记录 stdout / stderr / exit code
   ↓
推送 tool_result 事件
   ↓
写入审计日志
```

### 工具调用记录示例

```json
{
  "trace_id": "trace_000123",
  "session_id": "agent_session_789",
  "step_id": "step_005",
  "type": "tool_call",
  "tool_name": "run_command",
  "input": {
    "command": "npm test"
  },
  "output_summary": "12 passed, 0 failed",
  "exit_code": 0,
  "started_at": "2026-08-03T10:00:00Z",
  "ended_at": "2026-08-03T10:00:18Z",
  "policy_result": "allowed"
}
```

这样可以精确回答：

- 谁发起的？
- 哪个任务发起的？
- 哪个 Agent 发起的？
- 调用了什么工具？
- 输入是什么？
- 输出是什么？
- 是否成功？
- 耗时多少？
- 是否触发审批？
- 是否访问了敏感路径？

## 每一个输出如何被追踪？

Agent 的输出不只是聊天框里的最终回复，还包括：

- 代码 diff；
- 新增文件；
- 删除文件；
- 终端输出；
- 测试结果；
- 构建日志；
- 错误堆栈；
- 工具调用结果；
- commit message；
- PR 描述；
- 任务总结。

### 文件修改事件示例

```json
{
  "session_id": "agent_session_789",
  "step_id": "step_012",
  "type": "file_change",
  "path": "src/api/user.ts",
  "action": "modify",
  "diff": "@@ -12,7 +12,7 @@\n- if (!user) return null;\n+ if (!user?.id) return null;"
}
```

用户可以审查：

```text
Agent 为什么修改这个文件？
是在哪一步修改的？
修改前是什么？
修改后是什么？
修改后有没有运行测试？
测试结果如何？
如果测试失败，Agent 后续做了什么？
```

## 审计与回放：从实时展示到持久化追踪

实时可观测只是第一层。  
真正可审计，还需要把所有事件持久化保存。

### 事件流双通道架构

```text
Agent Runtime 产生事件
   ↓
Event Bus / 消息队列
   ↓
两个消费方向：
   1. SSE Gateway：实时推送给前端
   2. Audit Storage：持久化审计日志
```

### 审计日志通常包含哪些字段？

```json
{
  "trace_id": "trace_000123",
  "tenant_id": "tenant_abc",
  "workspace_id": "ws_123",
  "project_id": "project_456",
  "session_id": "agent_session_789",
  "task_id": "task_001",
  "step_id": "step_005",
  "event_type": "tool_call",
  "tool_name": "run_command",
  "actor": "cloud_agent",
  "input": {
    "command": "npm test"
  },
  "output_summary": "12 passed, 0 failed",
  "exit_code": 0,
  "started_at": "2026-08-03T10:00:00Z",
  "ended_at": "2026-08-03T10:00:18Z",
  "policy_result": "allowed"
}
```

### 审计能力可以做什么？

- 回放一次完整 Agent 任务；
- 查看 Agent 为什么修改某段代码；
- 检查是否执行过高危命令；
- 检查是否访问过敏感文件；
- 追踪某次事故对应哪一轮 Agent 任务；
- 分析某次失败发生在哪个步骤；
- 满足企业合规与安全审计要求。

## 全链路 Trace：把任务、步骤、工具调用串起来

为了做到“精确可追溯”，平台通常会使用 trace 体系，把整个任务链路串起来。

### Trace 层级示例

```text
trace_id：一次用户任务
session_id：Agent 会话
step_id：单个执行步骤
tool_call_id：单次工具调用
artifact_id：文件 diff / 日志 / 测试结果
```

### 一个完整任务链路

```text
用户提出需求
  trace_001
    step_001：理解需求
    step_002：搜索代码
      tool_call_001：search_code
    step_003：读取文件
      tool_call_002：read_file
    step_004：修改文件
      artifact_001：file_diff
    step_005：运行测试
      tool_call_003：run_command
    step_006：根据测试结果修复
    step_007：生成总结
```

如果最后出现问题，可以精确定位：

- 是哪一步引入了问题？
- 修改了哪个文件？
- 哪条命令失败？
- Agent 是否看到了错误日志？
- Agent 为什么做出某个决策？
- 最终输出是否遗漏了关键限制？

## 安全治理：高危操作必须经过策略控制

企业级 Cloud Agent 不能只靠模型判断是否安全，还需要平台级策略引擎。

### 常见允许操作

```text
读取项目文件
搜索代码
修改当前分支文件
运行测试
运行 lint
生成 commit
创建 PR
查看构建日志
```

### 常见限制操作

```text
删除仓库
强制推送
修改 CI/CD 配置
访问生产数据库
下载敏感目录
执行未知脚本
访问未授权外部域名
修改生产环境配置
上传代码到第三方服务
```

### 常见需要人工审批的操作

```text
合并 PR
部署到生产环境
执行数据库迁移
修改生产配置
安装未知依赖
执行高风险 shell 命令
访问敏感凭据
进行批量文件删除
```

### 策略控制的意义

Agent 不应该拥有无限制的“直接执行权”。

更合理的模式是：

```text
模型提出意图
   ↓
平台判断是否允许
   ↓
Sandbox 受控执行
   ↓
日志记录
   ↓
必要时人工审批
```

也就是说，Agent 拥有的是“建议权”和“受限执行权”，而不是任意操作权。

---

## Cloud Agent 相比本地 Agent 的优势

本地 Agent 直接运行在用户机器上时，可能存在以下问题：

```text
可以访问本机任意文件
可以读取环境变量
可以执行任意命令
可能接触生产凭据
行为难以统一审计
不同任务之间边界较弱
```

Cloud Agent 的优势在于统一管理：

```text
执行环境统一托管
权限统一控制
网络统一限制
日志统一收集
工具统一代理
产物统一审查
策略统一下发
```

因此更容易实现：

- 租户隔离；
- 权限最小化；
- 行为审计；
- 危险命令拦截；
- 任务回放；
- 企业合规；
- 数据安全治理。

Cloud AI Team 能做到：

```text
任务级 Sandbox 隔离执行

租户级资源与上下文隔离

+
受控工具调用代理
+
事件化 Agent Runtime

SSE 实时事件推送

全链路 trace

策略引擎与人工审批
```

## 需要注意的边界

虽然 Cloud Agent 可以大幅提升安全性与可观测性，但仍需理解几个边界：

1. **“每一步思考”不等于读取模型内部黑箱。**  
   平台能记录的是模型输出的推理事件、计划、消息和工具调用决策。

2. **“零数据渗透”是工程隔离目标，而不是模型能力。**  
   它依赖沙箱、权限、网络、凭据、审计等多层机制。

3. **安全性取决于平台配置和权限策略。**  
   如果用户主动授权了过高权限，平台仍需要配合审批、审计和策略控制来降低风险。

4. **可观测性依赖事件埋点和 Runtime 设计。**  
   Agent Runtime 越完善，能暴露的执行细节就越充分。
